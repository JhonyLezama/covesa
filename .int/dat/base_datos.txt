Buen ojo — justo ahí está la decisión importante: **property_statuses** y **project_statuses** tienen prácticamente los mismos campos (nombre, color, orden). Si los separas en dos tablas idénticas, es redundancia real. Te muestro las dos opciones y cuál recomiendo, y luego los campos completos de cada catálogo.

## Decisión de diseño: ¿tablas separadas o una tabla genérica de estados?

**Opción A — Tablas separadas** (lo que planteamos al inicio)
❌ Duplicas estructura (`property_statuses` y `project_statuses` son clones)
❌ Si mañana agregas `lead_statuses` o `referral_statuses`, sigues clonando tablas

**Opción B — Tabla genérica `statuses` con tipo (recomendada)**
✅ Una sola tabla para todos los estados del sistema, diferenciados por columna `type`
✅ Escalable: si después necesitas estados de leads o referidos, no creas tabla nueva, solo agregas filas
✅ Un solo panel de administración para gestionar "Estados" en vez de varios

Esta es la que te recomiendo. Así queda:

## Migraciones de ejemplo

```php
Schema::create('property_types', function (Blueprint $table) {
    $table->id();
    $table->string('name');
    $table->string('slug')->unique();
    $table->string('icon')->nullable();
    $table->text('description')->nullable();
    $table->boolean('is_active')->default(true);
    $table->unsignedInteger('order')->default(0);
    $table->timestamps();
});

Schema::create('zones', function (Blueprint $table) {
    $table->id();
    $table->string('name');
    $table->string('slug')->unique();
    $table->foreignId('parent_id')->nullable()->constrained('zones')->nullOnDelete();
    $table->string('department')->nullable();
    $table->decimal('latitude', 10, 7)->nullable();
    $table->decimal('longitude', 10, 7)->nullable();
    $table->boolean('is_active')->default(true);
    $table->unsignedInteger('order')->default(0);
    $table->timestamps();
});

Schema::create('statuses', function (Blueprint $table) {
    $table->id();
    $table->string('type'); // property | project | (futuro: lead, referral)
    $table->string('name');
    $table->string('slug');
    $table->string('color')->default('#0C447C');
    $table->unsignedInteger('order')->default(0);
    $table->boolean('is_active')->default(true);
    $table->timestamps();

    $table->unique(['type', 'slug']);
});
```

## Cómo se conectan a `properties` y `projects` (para que quede claro que no es solo teoría)

```php
Schema::create('properties', function (Blueprint $table) {
    $table->id();
    $table->foreignId('property_type_id')->constrained();
    $table->foreignId('zone_id')->constrained();
    $table->foreignId('status_id')->constrained('statuses'); // status_id, no property_status_id
    $table->foreignId('project_id')->nullable()->constrained();
    // ... resto de campos propios de la propiedad
});
```

**Regla práctica para no seguir cayendo en redundancia más adelante:** cualquier tabla que solo tenga "nombre + color/orden + on/off" y sirva para clasificar otra entidad, va a `statuses` (si es un estado) o se evalúa si merece su propio catálogo (si tiene lógica propia, como `property_types` que sí tiene ícono y descripción distintos).




Sigamos con `properties` y `projects` completas — estas son las tablas core del sistema, así que vale la pena detallar bien cada campo y por qué está ahí.

## Estrategia de borrado: Soft Deletes

Antes de las tablas, una decisión que afecta a todas: usar `SoftDeletes` en `properties`, `projects`, `blog_posts` y `leads`. Razón práctica: si un asesor "elimina" una propiedad vendida por error, o Google ya indexó una URL, prefieres poder recuperarla o al menos saber que existió, en vez de perder el registro para siempre.

```php
$table->softDeletes(); // agrega columna deleted_at
```

## Punto de diseño a validar contigo: ¿vale la pena tanta granularidad de traducción?

Aquí hay una decisión de costo/beneficio real: traducir la descripción de **cada propiedad individual** a 3 idiomas es trabajo manual recurrente para el cliente (cada vez que suban una propiedad nueva, deben escribir 3 versiones). Dos caminos:

1. **Traducción completa por propiedad** (lo que detallé arriba) — más profesional, más trabajo para ellos día a día
2. **Solo el contenido institucional y de proyectos se traduce** (Home, Nosotros, Servicios, landings de El Milagro/Hanan del Sol); **las fichas de propiedades individuales quedan solo en español**, ya que un inversionista extranjero interesado normalmente contacta al asesor directamente

Yo recomendaría la opción 2 para no generar fricción operativa al equipo comercial, pero es una decisión de negocio, no solo técnica — vale la pena preguntárselo directamente al cliente antes de programar la tabla `property_translations`.

## `media` (gestión centralizada de archivos)

En vez de repetir `featured_image`/`gallery` como JSON en cada tabla (properties, projects, leads), una alternativa más limpia es una tabla polimórfica de media, usando el patrón `morphMany` de Laravel:

| Campo | Tipo | Notas |
|---|---|---|
| id | bigint PK | |
| mediable_id | bigint | ID del modelo relacionado (polimórfico) |
| mediable_type | string | `Property`, `Project`, `BlogPost`, `Lead` |
| type | enum | `featured`, `gallery`, `attachment`, `document` |
| path | string | ruta del archivo en storage |
| original_name | string, nullable | nombre original al subir |
| mime_type | string, nullable | |
| size | integer, nullable | en bytes, útil para validar límites |
| order | integer, default 0 | orden en la galería |
| alt_text | string, nullable | para SEO/accesibilidad de imágenes |
| timestamps | | |

**Aquí hay una decisión de arquitectura importante que quiero que valides:** tienes dos caminos:

1. **JSON simple** (`gallery` como columna json en cada tabla) → más rápido de implementar, pero no puedes hacer analítica sobre archivos ("cuántas imágenes en total", "qué propiedades no tienen fotos"), ni reordenar/editar individualmente con facilidad desde el CMS
2. **Tabla `media` polimórfica** (la de arriba) → más flexible y escalable, permite un componente reutilizable de "galería" en el CMS para cualquier entidad, pero es una tabla más y relaciones morphMany que hay que manejar bien

Para este proyecto, con CMS "100% editable" como pidieron, yo recomiendo la **tabla `media` polimórfica** — porque el admin va a necesitar reordenar fotos, borrar una específica de la galería, marcar cuál es la portada, etc. Con JSON eso se vuelve más incómodo de manejar en el frontend del CMS.
